## Nura: The Intelligence Layer for Real Estate Development

Today, answering these questions requires stitching together data from dozens of fragmented sources—municipal zoning codes, flood maps, environmental databases, permit records, rental comps, demographic data. A single feasibility analysis can take an experienced analyst 20-40 hours and still miss critical risks. This friction slows deal velocity, increases capital costs, and causes good sites to be passed over.

**The Solution**

Nura is an AI-powered intelligence platform that transforms weeks of manual due diligence into minutes. We've built an agentic system that doesn't just retrieve data—it *reasons* across multiple sources simultaneously, synthesizes findings, and delivers institutional-grade analysis in natural language and structured reports.

Think of it as giving every developer access to a team of analysts who have instant recall of every zoning code, every flood zone, every comparable transaction, and every permit pathway in the country.

**Why Now**

Three converging forces make this the right moment:

1. **LLM capabilities** have crossed the threshold where AI can reliably interpret complex regulatory documents and synthesize multi-source analysis
2. **Data availability** has improved dramatically—most of the inputs we need are now digitized and accessible via API
3. **Market pressure**—rising interest rates and construction costs mean developers need to move faster and underwrite more precisely to make deals work

At a practical level, Nura has three core experiences:

- **1) Nura Chat (the copilot)**

### Layer 4: Similarity Scoring & Ranking

After filtering, you have ~6-20 comps. Now rank them by **similarity to subject**:

```python
def calculate_comp_score(subject: Property, comp: Property) -> float:
    """
    Returns 0-100 similarity score. Higher = better comp.
    """
    score = 0

    # Distance (closer = better) — 25 points max
    distance_miles = haversine(subject.coordinates, comp.coordinates)
    score += max(0, 25 - (distance_miles * 5))  # lose 5 pts per mile

    # Size similarity — 20 points max
    unit_diff_pct = abs(subject.total_units - comp.total_units) / subject.total_units
    score += max(0, 20 - (unit_diff_pct * 40))

    # Vintage similarity — 20 points max
    year_diff = abs(subject.year_built - comp.year_built)
    score += max(0, 20 - (year_diff * 2))  # lose 2 pts per year

    # Asset class match — 15 points
    if subject.asset_class == comp.asset_class:
        score += 15
    elif abs(ord(subject.asset_class) - ord(comp.asset_class)) == 1:
        score += 8  # adjacent class

    # Subtype match — 10 points
    if subject.subtype == comp.subtype:
        score += 10

    # Data quality — 10 points
    score += comp.source_confidence * 10

    return score

```

**9. Tips for New SDRs**

***This is the stuff that took me months to learn. Read it twice.***

**Mindset**

1. **You're not begging—you're offering value.** Nura saves people time and money. If they don't want it, that's fine, but you're not bothering them—you're giving them a chance to work smarter.
2. **Rejection is data, not failure.** Every "no" teaches you something. Every bad call makes the next one better. The only way to fail is to stop calling.
3. **Activity beats perfection.** A mediocre email sent is better than a perfect email stuck in drafts. Make the call. Send the message. You'll get better by doing.
4. **Curiosity is your superpower.** You're not there to pitch—you're there to understand. Ask questions. Listen. The best SDRs are the most curious.

**Tactics**

1. **Call first, email second.** Emails are easy to ignore. Calls break through. Make the call, then send the email as a follow-up.
2. **Research before you call (but don't over-research).** 2 minutes max. Know their name, company, and one thing about them. That's it. Move.
3. **Talk less, listen more.** If you're talking more than 30% of the call, you're talking too much. Ask a question and shut up.
4. **Always get a next step.** Never end a call without a clear next action. Demo scheduled? Great. Call back Thursday? Put it on the calendar. "I'll follow up" is not a next step.
5. **Send calendar invites immediately.** The second they agree to a meeting, send the invite while you're still on the phone. Meetings without invites don't happen.
6. **Log everything.** If it's not in the CRM, it didn't happen. Notes, next steps, dates—all of it.

**Common Mistakes to Avoid**

- **Pitching too early.** Don't vomit features. Ask questions first.
- **Talking about yourself.** They don't care about Nura. They care about their problems.
- **Being afraid of silence.** Ask a question and wait. Silence is uncomfortable—use it.
- **Taking "no" personally.** They're not rejecting you. They're busy. Call back later.
- **Giving up after one attempt.** It takes 8-12 touches to book a meeting. Most SDRs give up after 2.

## 🧠 Ontology Schema

The knowledge graph models real estate development intelligence as a connected entity graph. Every node is typed; every edge is labeled.

### Core Entity Types

| Entity Type | Description | Primary Source |
| --- | --- | --- |
| `Parcel` | Individual land parcel with PIN, geometry, acreage | County GIS / Regrid |
| `Jurisdiction` | Municipality — city, village, township, county | Census TIGER / Municode |
| `ZoningDistrict` | Zoning classification (R-1, C-2, PUD, etc.) | County GIS / Municode / eCode360 |
| `ZoningOrdinance` | Full text + parsed rules for a zoning district | Municode / eCode360 / American Legal |
| `TaxRecord` | Assessed value, taxable value, SEV, millage, exemptions | County Tax Assessor / Equalization Dept |
| `Owner` | Current owner entity (person, LLC, trust) | County Tax Assessor / Regrid |
| `Structure` | Existing building on parcel — type, sqft, year built | County Assessor / ATTOM |
| `Transaction` | Sale/transfer history — date, price, instrument | County Register of Deeds / ATTOM |
| `Permit` | Building permits, demolition, special use | Municipal permit portals |
| `EntitlementCase` | Rezoning, variance, site plan, PUD applications | Municipal meeting minutes / agendas |
| `FloodZone` | FEMA flood zone designation per parcel | FEMA NFHL |
| `Wetland` | NWI wetland boundaries overlapping parcels | USFWS NWI |
| `Utility` | Water, sewer, gas, electric service availability | Municipal GIS / utility providers |
| `SchoolDistrict` | School district boundaries + ratings | NCES / GreatSchools |
| `CensusBlock` | Demographics, income, population density | ACS / Census Bureau |

## ⚙️ Architecture

### Tech Stack

| Component | Technology | Rationale |
| --- | --- | --- |
| **Knowledge Graph DB** | Neo4j (AuraDB Pro) or Amazon Neptune | Native graph traversal for relationship queries; Cypher for dev speed |
| **Spatial Engine** | PostGIS (on Supabase or RDS) | Spatial joins, ST_Contains, ST_Touches, adjacency detection |

| **Ordinance Parser** | Custom NLP pipeline (GPT-4 / Claude structured extraction) | Parse setbacks, FAR, lot coverage, permitted uses from ordinance HTML |
| **ETL Orchestrator** | Prefect or Temporal | DAG-based pipelines per county with retry, monitoring, alerting |
| **File Storage** | S3 | Raw shapefiles, PDFs, scraped HTML |
| **Cache** | Redis | Geocoding cache, API rate limit tracking |
| **API Layer** | FastAPI | Serves graph queries to Nura frontend |

## 🔑 Key Design Decisions for Kevin

### 1. Graph DB Choice: Neo4j vs. Neptune

|  | Neo4j | Neptune |
| --- | --- | --- |
| Query language | Cypher (more expressive) | Gremlin / openCypher |
| Managed hosting | AuraDB | AWS native |
| Spatial support | Native spatial index | Need PostGIS sidecar anyway |
| Cost | ~$1K–3K/mo at our scale | ~$800–2K/mo |
| **Recommendation** | **Start here** — Cypher is faster to develop, spatial indexes help | Migrate later if AWS lock-in preferred |

### 2. Regrid vs. Direct County Scraping

Use Regrid as the **base parcel layer** for consistency, then **enrich with direct county data** where Regrid is incomplete (tax details, zoning spatial boundaries, permits). Regrid gives us nationwide coverage for 50-state expansion; county-direct gives us depth.

### 3. Ordinance Parsing Strategy

Don't try to build a universal ordinance parser. Instead:

1. Parse each municipality's ordinance into structured JSON using LLM extraction (Claude / GPT-4)
2. Store both raw HTML and structured extraction
3. Use human-in-the-loop validation for first pass per municipality
4. Re-run extraction when ordinance amendments detected

### 4. Entity Resolution for Owners

Michigan LLC records are at the state level (LARA). Cross-reference:

- County tax assessor owner name
- LARA LLC filings (Resident Agent, Registered Agent)
- Regrid owner data
- ATTOM deed records

Use fuzzy matching + LLM-assisted entity resolution to link "SMITH DEVELOPMENT LLC" across counties.

| --- | --- | --- |

| BS&A scraping blocked / rate-limited | Lose tax data for 22 counties | Negotiate bulk data purchase; cache aggressively |

| Regrid enterprise license delayed | No base parcel layer | Use county GIS direct for Tier 1 counties; Regrid as enrichment |
